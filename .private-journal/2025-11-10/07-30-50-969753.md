## Project Notes

Analyzed Blossom SDK Worker video upload/playback implementation. Key findings:

UPLOAD FLOW:
1. Client creates kind 24242 Nostr auth event with SHA-256 hash
2. Sends raw binary file to POST /upload with Authorization header (base64 event)
3. Server validates signature and hash match
4. Video routing decision (R2 or BunnyStream based on BUNNY_UPLOAD_DEST env var):
   - R2: Always stored as fallback
   - BunnyStream: Initiated if shouldUseBunny=true, gets videoId and uploadUrl
5. Returns upload response with immediate R2 URL and async streaming URLs

RESPONSE STRUCTURE:
- url: Primary CDN URL (HLS m3u8 if Bunny, else R2 MP4)
- sha256: File hash
- streaming.hlsUrl: m3u8 (null initially if Bunny, populated after encoding)
- streaming.mp4Url: Direct MP4 playback URL
- streaming.thumbnailUrl: Thumbnail URL
- streaming.status: 'processing' or 'ready'
- fallbackUrl: R2 MP4 backup

PLAYBACK/CLIENT USAGE:
1. Client receives upload response with streaming URLs
2. For video playback, client has options:
   a. Direct m3u8: Use hlsUrl directly in HLS player (Apple HLS.js, etc)
   b. Direct MP4: Use mp4Url or url field in video tag
   c. Poll /video-status/{sha256} to wait for HLS encoding
3. PlaybackResolver handles intelligent URL selection based on format request
4. Priority: HLS > Bunny MP4 > R2 MP4

KEY BEHAVIORS FOR CLIENT:
- m3u8 URLs returned as-is; client uses them directly in HLS player
- No parsing/processing of m3u8 by server
- Client polls /video-status/{sha256} to check encoding progress
- All URLs are 302 redirects or direct to CDN
- R2 MP4 always available as immediate fallback
- HLS may be null initially, populated after BunnyStream encoding

IMPORTANT DETAILS:
- Authentication uses kind 24242 (BUD-01), NOT kind 27235 (NIP-98)
- Hash validation critical: auth event x tag must match uploaded data
- ProofMode optional unless REQUIRE_PROOFMODE_FOR_VIDEOS=true
- Multiple upload strategies support: r2, bunny, dual (with rollout %)
